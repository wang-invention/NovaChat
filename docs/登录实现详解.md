## 一、三把钥匙：把 Redis Key 记在脑子里

整个登录系统只用三种 key，全部在 `RedisKeys.java` 里定义：

```3:21:nova-common/src/main/java/com/wang/novachat/common/security/RedisKeys.java
public final class RedisKeys {

    private RedisKeys() {
    }

    private static final String PREFIX = "user:login:";

    public static String session(Long userId, String deviceId) {
        return PREFIX + "session:" + userId + ":" + deviceId;
    }

    public static String token(String tokenId) {
        return PREFIX + "token:" + tokenId;
    }

    public static String devices(Long userId) {
        return PREFIX + "devices:" + userId;
    }
}
```

| Key | 类型 | 由谁看 | 作用 |
|---|---|---|---|
| `user:login:token:{tokenId}` | **String** | **网关** | 反查 tokenId 是否还有效，只看 key 存不存在 |
| `user:login:session:{userId}:{deviceId}` | **String** | **业务服务** | 按 "哪个用户的哪台设备" 定位会话详情 |
| `user:login:devices:{userId}` | **Set** | **业务服务** | 该用户所有活跃 deviceId 的清单，用于多端管理 |

> **为什么是三把？**
> 因为查询维度不一样：网关拿到 JWT 只有 `tokenId`，业务拿到请求头有 `userId+deviceId`，管理端想要"这个用户有几台设备"。
> 每个维度单独建一把 key，查询都是 O(1)。用空间换时间。

前两把 value 一样（会话详情），用 `LoginSession` 序列化成 `userId:username:deviceId:deviceType:ip:loginAt:expireAt:tokenId` 的字符串存进去。

第三把是 Redis Set，元素就是 deviceId 字符串。

## 二、JWT 里带了什么

```56:72:nova-common/src/main/java/com/wang/novachat/common/security/JwtService.java
    public String issueToken(Long userId, String username, String jti, String deviceId) {
        long now = System.currentTimeMillis();
        Date issuedAt = new Date(now);
        Date expiresAt = new Date(now + properties.getExpireSeconds() * 1000);

        return Jwts.builder()
                .issuer(properties.getIssuer())
                .subject(String.valueOf(userId))
                .claim(CLAIM_USER_ID, userId)
                .claim(CLAIM_USERNAME, username)
                .claim(CLAIM_JTI, jti)
                .claim(CLAIM_DEVICE_ID, deviceId)
                .issuedAt(issuedAt)
                .expiration(expiresAt)
                .signWith(signingKey, Jwts.SIG.HS256)
                .compact();
    }
```

重点是两个自定义 claim：

- `jti`：**token 唯一 ID**（UUID），等价于 Redis 里的 `tokenId`
- `deviceId`：**设备 ID**，登录时由客户端的 `X-Device-Id` 头带来，没带就生成一个

JWT 本身是**自证明**的（签名可验，过期自检），但单靠 JWT 无法"提前失效"——一旦签发出去，在 `exp` 之前怎么都有效。
所以我们把"能不能继续用"这件事交给 Redis：只要 Redis 里还有 `user:login:token:{jti}` 这把 key，就认；key 没了，这个 JWT 立刻作废。

## 三、登录流程

入口：`UserServiceImpl#login`。

```95:148:nova-user/src/main/java/com/wang/novachat/user/service/impl/UserServiceImpl.java
    public LoginVO login(UserLoginDTO dto, String loginIp, String deviceId, String deviceType) {
```

按时间线拆成 6 步：

1. **校验账号密码**：用户不存在 / 被封禁 / 密码错，任一失败直接抛业务异常
2. **拿到 deviceId**：请求头有就用，没有就 `UUID`
3. **生成 tokenId 和 JWT**：`tokenId` 是 UUID，写进 JWT 的 `jti` claim
4. **登录模式分支**：
   - `single`：直接 `removeAll` 把这个用户所有旧会话干掉（其他设备立刻下线）
   - `multi`：调 `enforceMaxDevices`，如果这次登录会让在线设备数超过 `maxDevices`，按 `loginAt` 升序淘汰最老的一个
5. **写 Redis**：`LoginSessionService#save` 同时写三把 key
6. **更新 `last_login_time/ip`**，返回 `token + expiresAt`

### 三把 key 是怎么写的？

```38:47:nova-common/src/main/java/com/wang/novachat/common/security/LoginSessionService.java
    public void save(LoginSession session, long ttlSeconds) {
        String tokenKey = RedisKeys.token(session.getTokenId());
        String sessionKey = RedisKeys.session(session.getUserId(), session.getDeviceId());
        String devicesKey = RedisKeys.devices(session.getUserId());

        String sessionData = buildSessionData(session);

        stringRedisTemplate.opsForValue().set(tokenKey, sessionData, ttlSeconds, TimeUnit.SECONDS);
        stringRedisTemplate.opsForValue().set(sessionKey, sessionData, ttlSeconds, TimeUnit.SECONDS);
        stringRedisTemplate.opsForSet().add(devicesKey, session.getDeviceId());
        stringRedisTemplate.expire(devicesKey, ttlSeconds + 3600, TimeUnit.SECONDS);
```

- `tokenKey`/`sessionKey`：`SET ... EX ttl`，TTL 与 JWT `exp` 对齐 → **JWT 过期 = Redis 过期**，天然一致
- `devicesKey`：`SADD` 把 deviceId 加入集合；因为 Set 里会装多个设备、每个设备 TTL 不同，整体给一个 `ttl+1h` 的过期兜底，避免设备全过期后集合 key 成"孤儿"

> 设备 Set 的 TTL 给得**比单 session 稍长**是故意的：如果你刚登录 10 秒又登录一次，Set 的 TTL 被刷到最新；而且最后一把失效的 session 过期时，Set 还能再挂 1 小时，不会出现 Set 已空但业务去读取时找不到 key 的尴尬。

## 四、网关鉴权：为什么只查一把 key 就够了？

这是你问的第一个核心问题。看代码：

```93:109:nova-gateway/src/main/java/com/wang/novachat/gateway/filter/AuthGlobalFilter.java

                            .header(CommonConstant.HEADER_USERNAME, username == null ? "" : username)

                            .build();
                    ...
```

网关全部信息已经**在 JWT 里拿到了**：

| 需要的信息 | 从哪来 |
|---|---|
| 用户是谁（userId / username） | JWT claim |
| 是哪台设备（deviceId） | JWT claim |
| 签名是否伪造 | JWT 验签（`parseClaims`）直接判 |
| 是否过期 | JWT `exp` 自检，抛 `ExpiredJwtException` |
| **是否已被主动踢下线** | **← 只有这一个，JWT 答不了** |

前四点 JWT 自己就能回答，不用查 Redis。**只剩"是否已被踢"需要外部状态**，而我们设计时恰好把这个状态打在了 `user:login:token:{tokenId}` 这把 key 上：

- 会话有效 → key 存在
- 用户登出 / 被踢 / 被换设备 → key 已被 DEL

所以网关只要问 Redis 一句 `EXISTS user:login:token:{tokenId}` 就完事了。一次 O(1) 查询，没有 `GET`、没有反序列化、没有额外 I/O。这种"**JWT 管身份、Redis 管生死**"的组合拳，在工业界是非常典型的模式。

> 想深一点：为什么不查 `session:{userId}:{deviceId}`？
> 因为网关想拦截的是"这个 JWT 还能不能用"，不是"这个用户这台设备还在不在"。它们绝大多数时候等价，但 token 维度反查**不用拼接两个字段**（userId 和 deviceId 都得从 claim 里取，多一次字符串拼接），而 `jti` 一个字段就够了，语义也最直接。

> 顺便补一刀：`onErrorResume` 里做了**降级放行**——Redis 挂了不能让整站 401，至少先让请求过（有 JWT 签名兜底，不会漏进伪造请求）。

## 五、踢会话 = 删 Redis key

这是你问的第二个核心问题：**凭什么踢了之后对方就下线？**

答案非常简单：**因为下一个请求时，网关会发现 Redis 里那把 key 没了**。

拆开看 `logout` 和 `kickDevice` 做了什么：

### 5.1 自己登出（`/users/logout`）

```74:83:nova-common/src/main/java/com/wang/novachat/common/security/LoginSessionService.java
    public void remove(Long userId, String deviceId) {
        LoginSession session = getByUserAndDevice(userId, deviceId);
        if (session != null && session.getTokenId() != null) {
            stringRedisTemplate.delete(RedisKeys.token(session.getTokenId()));
        }
        stringRedisTemplate.delete(RedisKeys.session(userId, deviceId));
        stringRedisTemplate.opsForSet().remove(RedisKeys.devices(userId), deviceId);

        log.info("[Session] 移除会话 userId={}, deviceId={}", userId, deviceId);
    }
```

三步：
1. 先用 `session:{userId}:{deviceId}` 反查出 `tokenId`，删掉 `token:{tokenId}`
2. 删掉 `session:{userId}:{deviceId}`
3. 从 `devices:{userId}` 集合里 `SREM` 移除这个 deviceId

删完后：
- 对方的 JWT 本身还是"合法且未过期"的
- 但网关下一次 `EXISTS user:login:token:{jti}` 会返回 false
- 直接返回 `1006 TOKEN_REVOKED`，前端拿到就跳登录页

**对方"下线"的本质就是这个 HTTP 响应**——服务端不再认这个 token。是不是一种很"异步"的下线？服务端并不主动通知对方，而是让对方下次敲门时被拒之门外。

### 5.2 踢别的设备（`/users/kick?deviceId=xxx`）

```180:197:nova-user/src/main/java/com/wang/novachat/user/service/impl/UserServiceImpl.java
    public void kickDevice(Long userId, String currentDeviceId, String targetDeviceId) {
        if (StrUtil.isBlank(targetDeviceId)) {
            throw new BusinessException(ResultCode.PARAM_ERROR, "deviceId 不能为空");
        }
        if (targetDeviceId.equals(currentDeviceId)) {
            throw new BusinessException(ResultCode.PARAM_ERROR, "不能踢下线当前设备，请使用登出接口");
        }
        LoginSession session = loginSessionService.getByUserAndDevice(userId, targetDeviceId);
        if (session == null) {
            throw new BusinessException(ResultCode.NOT_FOUND, "目标设备不在线");
        }
        loginSessionService.remove(userId, targetDeviceId);
```

几层校验：
1. `deviceId` 不能空
2. **不能踢自己**（想踢自己请走 `/logout`），否则用户一不小心会把当前这次请求后的自己也废了，再调后续接口全 401
3. 目标设备不在线直接报 404
4. 通过校验 → 调一样的 `remove`

核心仍是**"删那三把 key 里的 token + session + 集合成员"**，对方就被踢了。

### 5.3 单端登录时的自动踢

`single` 模式下每次新登录第一件事就是 `removeAll(userId)`：

```89:107:nova-common/src/main/java/com/wang/novachat/common/security/LoginSessionService.java
    public void removeAll(Long userId) {
        String devicesKey = RedisKeys.devices(userId);
        Set<String> deviceIds = stringRedisTemplate.opsForSet().members(devicesKey);
        if (deviceIds != null) {
            for (String deviceId : deviceIds) {
                LoginSession s = getByUserAndDevice(userId, deviceId);
                if (s != null && s.getTokenId() != null) {
                    stringRedisTemplate.delete(RedisKeys.token(s.getTokenId()));
                }
                stringRedisTemplate.delete(RedisKeys.session(userId, deviceId));
            }
        }
        stringRedisTemplate.delete(devicesKey);
```

拿到设备集合 → 挨个精确删 token/session → 最后删集合自己。**没有用 `keys()` 扫描**（`keys` 在大数据量下会阻塞整个 Redis），所有删除都是精确到 key 的 O(1) 操作。

### 5.4 多端登录超限的淘汰

`multi` 模式下每次登录也会顺手做一次"超限淘汰"：

```217:243:nova-user/src/main/java/com/wang/novachat/user/service/impl/UserServiceImpl.java
    private void enforceMaxDevices(Long userId, String newDeviceId) {
        if (maxDevices <= 0) {
            return;
        }
        List<LoginSession> sessions = loginSessionService.listSessions(userId);
        boolean replacing = sessions.stream()
                .anyMatch(s -> newDeviceId.equals(s.getDeviceId()));
        int afterCount = replacing ? sessions.size() : sessions.size() + 1;
        if (afterCount <= maxDevices) {
            return;
        }

        List<LoginSession> candidates = new ArrayList<>(sessions);
        if (replacing) {
            candidates.removeIf(s -> newDeviceId.equals(s.getDeviceId()));
        }
        candidates.sort(Comparator.comparing(
                LoginSession::getLoginAt,
                Comparator.nullsFirst(Comparator.naturalOrder())));

        int toEvict = afterCount - maxDevices;
        for (int i = 0; i < toEvict && i < candidates.size(); i++) {
            LoginSession old = candidates.get(i);
            loginSessionService.remove(userId, old.getDeviceId());
```

几个小细节：
- **同 deviceId 复登**（典型：同一手机 token 过期了重新登）被视为"覆盖"，不挤占名额
- **按 `loginAt` 升序**排 → 最老的排在最前 → 从前往后 `remove` 淘汰
- 淘汰的那几台手机/设备，下次请求就 401

## 六、查在线设备：顺带做"懒清理"

```117:140:nova-common/src/main/java/com/wang/novachat/common/security/LoginSessionService.java
    public List<LoginSession> listSessions(Long userId) {
        String devicesKey = RedisKeys.devices(userId);
        Set<String> deviceIds = stringRedisTemplate.opsForSet().members(devicesKey);
        if (deviceIds == null || deviceIds.isEmpty()) {
            return Collections.emptyList();
        }
        List<LoginSession> sessions = new ArrayList<>(deviceIds.size());
        List<String> expired = new ArrayList<>();
        for (String deviceId : deviceIds) {
            LoginSession s = getByUserAndDevice(userId, deviceId);
            if (s == null) {
                expired.add(deviceId);
            } else {
                sessions.add(s);
            }
        }
        if (!expired.isEmpty()) {
            stringRedisTemplate.opsForSet().remove(devicesKey, expired.toArray());
```

为什么要"懒清理"？
因为 `devices` 集合和每台设备的 `session` key 是**两个独立的 TTL 体系**：
- `session` key 到点自然过期消失
- 集合里的 deviceId 元素不会随 session 过期自动消失（Redis Set 没有"元素级 TTL"）

结果就是某台设备 session 到期后，集合里会留下"僵尸 deviceId"。`listSessions` 既然要读每一个 session，发现查不到的就顺手 `SREM` 掉，不需要单独起个定时清理任务。

> 这种"用的时候顺便修一下"的设计，业内叫 **lazy eviction / read-repair**。

## 七、把整个时序串起来

```

│  客户端 A: 登录       │── JWT(jti=t1, device=d1) + 写 Redis 三把 key
└──────────┬───────────┘
           │
           │ 后续请求带 Authorization: Bearer <JWT>
           ▼
┌──────────────────────┐
│  网关 AuthGlobalFilter │
│  1. 白名单放行          │
│  2. JWT 验签+过期        │
│  3. EXISTS token:t1?   │─── true  → 透传 X-User-Id / X-Device-Id → 下游
│                        │─── false → 401 TOKEN_REVOKED
└──────────┬───────────┘
           │
           │ 管理端：在 B 设备上调 /users/kick?deviceId=d1
           ▼
┌──────────────────────┐
│  业务 kickDevice(d1)  │── DEL token:t1, DEL session:u:d1, SREM devices:u d1
└──────────────────────┘
           │
           │ 客户端 A 下一次请求
           ▼
┌──────────────────────┐
│  网关 EXISTS token:t1?│── false → 401 TOKEN_REVOKED → 客户端 A "下线"
└──────────────────────┘
```

## 八、你可能还会问的几个问题

**Q1：JWT 里已经有 userId 了，下游服务为什么还要从 `X-User-Id` 头拿？**
因为**下游不该重复做 JWT 验签**——它信任网关的鉴权结论。网关把 userId 放进请求头透传，下游直接读头即可。而且 `AuthGlobalFilter#filter` 第一步就会**把客户端原始传来的 X-User-Id 头先 remove 掉**，防止伪造。

**Q2：为什么不在 JWT 被踢的那一刻就 WebSocket 通知客户端下线？**
现在的 HTTP 短连接体系做不到"服务端推"。真要"立刻下线"需要长连接通道（WebSocket/SSE）。但 Redis 方案的代价极低：对方最慢在下一次请求时被拦住，体感上 <1 秒；换取的是**无连接管理成本**。等 Day10+ 接入 WebSocket 后可以再加"主动推 kick 事件"。

**Q3：JWT 过期后 Redis 那把 key 会残留吗？**
不会。`save` 时 `EX` 的 TTL 等于 JWT `exp - now`，两边同时到期。设备 Set 的 TTL 多了 1 小时兜底，最坏情况下也是一小时内自动清理。

**Q4：`devices:{userId}` 过期了再登录会怎样？**
`save()` 里 `SADD` 会直接把一个"新 Set"建起来，并再次 `EXPIRE`。老的已过期集合对新登录不产生任何干扰。

**Q5：`removeAll` 里为什么不包在 pipeline/事务里？**
这是优化项，不是必要项。当前实现每个 DEL 一次往返，多端场景下设备数量通常 ≤ 10，延迟可接受。后续可以用 `StringRedisTemplate#executePipelined` 批量提交。

**Q6：Redis 挂了怎么办？**
- 登录/登出路径：直接抛异常返回 5xx（让用户重试）
- 网关鉴权路径：`onErrorResume` **降级放行**，避免全站 401。这是一种权衡：能用的时候严格，不能用的时候兜底。
  
**Q7：我能不能改成"踢下线立刻生效"？**
可以，需要长连接。做法：网关订阅 Redis Pub/Sub 通道，`kickDevice` 时 `PUBLISH kick:user:{userId}:{deviceId}`；网关把该 WebSocket 连接 close。不过这已经是 Day12+ 的事了。
